# RAG 知识库问答：双路召回 · RRF 融合 · 引用溯源

一个从 0 搭起来的最小 RAG 检索层，不依赖 LangChain 或向量数据库。重点不是接上大模型，而是**把检索效果变成可复算的数字**：同一份语料、同一套标注，换方案就能看到指标涨还是跌。

**结果：直接问法 Recall@5 = 1.000、MRR = 0.969；口语化硬查询 Recall@5 从 BM25 的 0.633 提升到 0.667，MRR 0.591。**

## 实测指标

60 篇 LLM / RAG 主题短文（8 个分类），两套自建评测集。标注口径：能直接回答该问题的文档算相关。

**A. 直接问法集（48 条）** —— 问法与文档表述接近

| 方案 | Recall@5 | MRR@20 |
|---|---|---|
| BM25 | 1.000 | 0.958 |
| 字符 TF-IDF | 1.000 | 0.964 |
| **混合 + RRF** | **1.000** | **0.969** |

**B. 口语化硬查询集（30 条）** —— 换词、间接问法，例如「公司想把内部资料接进大模型，又不想重新训练参数」

| 方案 | Recall@1 | Recall@5 | MRR@20 |
|---|---|---|---|
| BM25 | 0.500 | 0.633 | 0.579 |
| 字符 TF-IDF | 0.467 | 0.667 | 0.568 |
| **混合 + RRF + 标题加权** | **0.533** | **0.667** | **0.591** |

直接问法下三路都已接近天花板，说明这套语料本身不难；真正拉开差距的是口语化问法。绝对分数不高是预期的——硬查询集是故意挑的难例，用来看方案之间的相对差异，不用来宣称"准确率 XX%"。

## 架构

```
60 篇领域文档 / 8 个分类
   ├── 词级 BM25（jieba 分词，标题加权 2 倍）
   └── 字符二元组 TF-IDF（不依赖分词，兜底错词与新词）
                ↓
        RRF 倒数排名融合（k = 60）
                ↓
         Top-K 片段 + 引用编号
                ↓
   抽取式回答 / 可选 LLM 生成（OpenAI 兼容接口）
```

## 快速开始

依赖 Python 3.10+，无外部服务。

```bash
pip install -r requirements.txt

python eval.py        # 直接问法集，输出 eval_results.json
python eval_hard.py   # 口语化硬查询集，输出 eval_hard_results.json

python -m uvicorn service:app --port 18090
curl "http://127.0.0.1:18090/search?q=怎么抑制幻觉&k=3"
curl -X POST localhost:18090/ask \
  -H 'Content-Type: application/json' \
  -d '{"question":"公司想把内部资料接进大模型，又不想重新训练参数","top_k":5}'
```

`/search` 支持 `mode=bm25|tfidf|hybrid|hybrid_rm3`，用来复现上表的每一行。

生成层可选：设置 `LLM_BASE_URL` / `LLM_API_KEY` / `LLM_MODEL` 即走 OpenAI 兼容接口；未配置时返回**带引用编号的抽取式结果**，不会编造内容。

## 一次失败的尝试（保留在代码里）

实现了 RM3 伪相关反馈（用首轮 top-8 文档的高权重词扩展查询），结果在口语化集上 **Recall@1 从 0.533 掉到 0.467、MRR 从 0.591 掉到 0.568**。

原因是 60 篇短文语料里，扩展出来的词噪声很大，把无关词带进了查询。结论是**不上线**，并把这个负结果写进 README，而不是删掉只留好看的数字。`hybrid_rm3` 模式仍可通过 `/search` 复现该结论。

## 关键设计取舍

1. **为什么用两路召回**：BM25 对专有名词、编号、术语敏感；字符 TF-IDF 不依赖分词，能兜住分词错误和新词。两路错开的样本不完全重合，融合后更稳。
2. **为什么用 RRF 而不是加权求和**：BM25 与余弦的分数不同量纲，加权求和要先归一化再调权重，换语料就失效；RRF 只看名次，几乎无参数（k 取 60 是常用默认值）。
3. **为什么默认抽取式**：检索和生成解耦，先确认召回没问题，再接模型。否则分不清是召回错还是生成错。

## 已知限制

- 语料只有 60 篇、78 条评测样本，**规模不足以支撑"生产可用"的结论**；指标只用于方案间横向对比。
- 第二路是字符二元组 TF-IDF，**不是 embedding / 向量检索**，语义泛化能力有限。
- 评测集自建且为单标注，存在主观性；未做多人标注一致性校验。
- 生成层没有做流式输出、重排（cross-encoder）和权限过滤，仅演示接口形态。

## 可以继续做的方向

1. 把字符 TF-IDF 换成中文 embedding，对比混合检索的增益还剩下多少。
2. 引入 cross-encoder 重排，观察 Recall@5 与 P99 延迟的权衡。
3. 把 30 条硬查询扩到 200 条，并做双人标注 + 一致性统计。
